# 项目开发原则

状态：Active

本文件定义 Poopornot 当前开发应遵循的长期原则。与单项功能规格冲突时，应先更新本文件或通过 ADR 记录例外。

## 1. 产品原则

### 1.1 先解决即时需求

核心任务是让用户尽快找到可用厕所。界面决策应优先减少查询和导航步骤，不用营销页或说明页阻挡地图主流程。

### 1.2 定位可用，但不能成为唯一入口

定位成功时优先使用当前位置；定位失败、不准确、被拒绝或用户计划查询其他城市时，必须允许选择城市和具体地点。

### 1.3 不夸大数据完备性

高德 POI 结果不是全国厕所的完整清单。本地 `toilet` 状态未核实时必须使用 `2`，不能因界面需要把未知写成“有”或“无”。

### 1.4 使用平台自然能力

在微信小程序中优先使用 `wx.openLocation` 等平台原生能力；只有当内部路线能带来明确价值时，才承担额外 API 配额和交互复杂度。不同客户端允许根据平台能力保留不同实现。

## 2. 工程原则

### 2.1 一个后端服务多个客户端

网页、小程序和 Android 应共用统一 API 和业务数据，避免复制高德请求逻辑与密钥。新增接口时同步评估三个客户端兼容性。

### 2.2 当前代码是现状事实来源

README、旧笔记和对话用于解释背景；判断当前行为时以实际代码、配置和数据为准。文档发现冲突时必须明确记录，不得静默选择方便的说法。

### 2.3 控制外部依赖成本

高德请求应分页、限速、去重和缓存。不得恢复地铁逐站请求模式。增加自动刷新、扩大结果上限或新增查询入口前，必须估算外部 API 调用次数。

### 2.4 变更范围清晰

不要把平台特有需求强行推广到其他客户端。例如小程序取消路线不自动等于网页和 Android 也应取消；跨平台统一需要独立决策。

### 2.5 错误必须可恢复

外部 API 错误不能让后端进程退出。客户端应保留手动城市入口，服务端应返回稳定 JSON 错误，并在可行时返回部分结果。

## 3. 数据原则

### 3.1 状态与坐标分离

`data/metro` 维护稳定的人工信息：线路、站名、线路颜色和厕所状态；高德负责坐标。不要把未经验证的 `location` 写回线路 JSON。

### 3.2 单一共享数据源

地铁状态只维护在 `data/metro`。不得在小程序或 Android 中复制一套独立地铁 JSON。

### 3.3 未知优于错误

`toilet: 2` 表示“待确认”，显示为橙色。只有存在可靠来源时才使用 `1` 或 `0`。后续引入用户投票时，原始投票与审核后的有效状态应分开保存。

### 3.4 跨城市以距离为准

附近地铁站按基准点空间范围筛选，不因行政区边界排除邻市站点。

## 4. 安全与隐私原则

### 4.1 最小化定位使用

只为当前查询和导航请求一次定位，不进行后台持续定位。除非另有经过评审的功能规格，不在服务器持久化用户位置和搜索历史。

### 4.2 密钥按暴露模型管理

- `AMAP_WEB_SERVICE_KEY` 只在后端。
- 浏览器必须获得的 JS Key 依赖域名白名单限制。
- Android Key 依赖包名和签名限制。
- 示例文件只能使用占位符，不得放入真实密钥。

### 4.3 生产网络默认 HTTPS

微信小程序和公开 API 必须使用有效 HTTPS 域名。明文 HTTP 只允许在明确隔离的本地开发场景使用。

### 4.4 权限说明应对应真实行为

小程序和 Android 的定位权限说明、隐私文本、平台申报与代码行为必须一致。新增采集、存储、分享或第三方 SDK 前先更新隐私文档。

## 5. 文档与变更治理

### 5.1 每次修改都记录

任何业务代码、配置、数据或正式文档修改都应追加到 `CHANGELOG.md`，保留既有历史，不覆盖或清空。

### 5.2 文档状态明确

- `Draft`：尚未完成或需要决策。
- `Active`：与当前实现一致，可执行。
- `Deprecated`：仅保留历史用途。

每份新文档先以 `Draft` 建立骨架，再在核验后提升为 `Active`。无法确认的信息必须写“待确认”。

### 5.3 重大决策使用 ADR

影响多个客户端、数据模型、部署或长期维护成本的决定，使用 `docs/adr/` 记录背景、备选方案、决策和后果。

### 5.4 功能使用规格驱动

较大功能先从 `docs/specs/_template/` 创建规格、计划和任务清单，再实现、验证和发布。

## 6. 完成定义

一次变更至少满足：

1. 行为符合规格，未破坏平台差异。
2. 相关语法、构建或人工流程已验证；无法运行的检查已说明。
3. API、配置、数据规则和安全影响已同步文档。
4. `CHANGELOG.md` 已追加记录。
5. 未把密钥、个人路径、签名材料或用户数据写入仓库。

## 7. 待确认

- 本原则的批准人、评审周期和例外批准流程。
- 是否要求所有重大变更必须先提交 ADR 或功能规格。
