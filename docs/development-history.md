# 开发历史

状态：Active

本文根据开发对话、当前代码、现有 `CHANGELOG.md` 和辅助开发笔记恢复。精确提交日期无法由现有材料确认时，使用阶段或月份描述，不把推测写成事实。

## 1. 起点：网页 MVP（2026-06）

项目最初以“拉了么”或“去哪儿啦”为候选名称，目标是先做一个地图为主体的网页：获取用户位置、查找附近公共厕所，并把其他控件悬浮在地图上。

早期关键选择：

- 采用高德地图覆盖中国地图、定位和 POI 搜索需求。
- 先实现网页，再迁移到微信小程序。
- 高德 Key 不直接硬编码在网页业务代码中，改由 Node 后端读取 `.env`。
- `AMAP_JS_KEY` 和 `AMAP_SECURITY_JS_CODE` 通过 `/api/config` 提供给浏览器；`AMAP_WEB_SERVICE_KEY` 只在后端调用 Web Service。

网页随后加入：

- 高德地图与浏览器定位。
- 公共厕所周边搜索和列表。
- 点击厕所标记后展示详情与“路线”按钮。
- 高德步行路线查询和地图折线绘制。
- 浅色/深色主题切换。

## 2. 半径、分页与结果面板调整

厕所查询最初长期只返回 25 条，开发过程中确认高德单页结果上限为 25。后端改为分页请求、去重和最多返回 100 条；随后又加入分页间隔和在限流时返回部分结果的处理。

网页 UI 从底部堆叠结果改为左侧约五分之一宽的可滚动结果栏，保留地图作为主视觉。搜索流程也从“输入关键词直接把结果都当厕所”调整为两步：先选择城市和具体地点，再以该地点为基准按半径查厕所。

定位基准曾错误落在城市中心，后来改为：定位成功时优先使用当前坐标；只有用户认为定位不准或主动查其他城市时，才手动切换城市和地点。

## 3. 地铁厕所数据加入

地铁功能最初只建立无锡 1 号线 JSON，前端地图却能显示多条真实线路，因为高德底图本身绘制了地铁线路。由此形成了后来的职责划分：

- 地图供应商负责真实线路几何和底图颜色。
- 项目只叠加站点厕所状态。
- 本地 JSON 只维护站名、线路元数据和 `toilet`，不维护坐标。

早期曾尝试在 JSON 中保存 `location` 并连接站点画线，后来因为坐标不准确、直线不符合真实线路而移除。后端改为按站名从高德匹配坐标。

无锡 1、2、3、4 号线随后全部录入，并根据当时结论统一标为 `1`。之后补充南京及跨市线路目录，并建立 `city_index.json` 作为全国有轨道交通城市的目录规划。

## 4. 地铁 QPS 与加载性能优化

最初后端为每一个地铁站单独调用高德，导致首次加载等待十几秒，并频繁出现 `CUQPS_HAS_EXCEEDED_THE_LIMIT`。

解决方案演变为：

1. 每个城市分页查询“地铁站”POI。
2. 建立站名到坐标的城市级索引。
3. 用本地 JSON 站名批量匹配。
4. 在同一 Node 进程内缓存城市索引。

后续又加入基准点附近地铁站的高德周边搜索作为兜底，并把筛选逻辑从“当前城市是否有线路文件”改为“站点是否落在基准点半径内”。这一变化解决了句容、马鞍山和城市边界附近无法看到邻市地铁站的问题。

## 5. 微信小程序开发（2026-06 至 07）

网页能力被迁移到 `WhereToPoop/`。小程序使用微信原生 `map` 组件显示腾讯地图底图，但地点、厕所、逆地理编码和地铁坐标仍通过统一后端调用高德，因此不需要 `AMAP_JS_KEY` 或 `AMAP_SECURITY_JS_CODE`。

小程序演变包括：

- 从独立目录迁回正式项目根目录下的 `WhereToPoop/`。
- 启动时优先使用当前位置，不再固定无锡市中心。
- 反向解析实际城市，修复城市按钮总显示“无锡”的问题。
- 城市与地点改为同一行；城市使用推荐城市和字母索引选择器。
- 地点按钮改为“搜地点”，地点候选使用普通地点标记。
- 半径调整为 300 m、500 m、1 km、3 km，改变半径后自动查询，同时保留“查厕所”。
- 首次定位完成后自动查询默认 500 m 内厕所。
- 结果区域扩大并可滚动，修复部分按钮超出页面的问题。
- 地图右上角保留定位、地铁和昼夜切换按钮；定位图标改为图片资源。
- “铁”按钮展示最近 10 个地铁站；列表加入厕所状态点和导航。
- 加入好友/朋友圈分享与 `UpdateManager`。

开发中还处理过微信旧编译链不支持 `??` 和可选链导致的预览语法错误。

## 6. 小程序导航功能的增加、修复与移除

小程序最初复用了网页路线能力：调用后端 `/api/navigation`，在小程序地图内画步行路线。期间修复了两类问题：

- 高德返回 `OVER_DIRECTION_RANGE` 时未被捕获，导致后端进程退出。
- 选中某厕所后路线错误指向另一个厕所，修正了目标坐标绑定。

随后产品决策发生变化：小程序更适合使用微信原生位置页，让用户继续选择腾讯、高德、百度等地图应用。最终当前实现为：

- 厕所和地铁站结果只保留“导航”。
- 详情页只保留“导航”。
- 使用 `wx.openLocation`。
- 删除小程序内路线状态、折线、结果页和 `/api/navigation` 客户端封装。

网页和 Android 的后端步行路线没有随之删除。

开发对话中曾短暂讨论自制目的地详情页和导航选择页，用户随后要求撤回；当前没有该自制页面。

## 7. 主题与地图样式

网页使用高德 `normal` / `dark` 样式，可完整切换地图与 UI。

小程序加入 UI 夜间模式后发现底图不会自动变暗。曾加入腾讯位置服务 subkey 和深浅样式 ID 的条件双地图分支，但未配置样式时在真机出现“marker 和署名存在、道路瓦片空白”。2026-08-05 恢复为单一常驻原生默认地图；当前夜间按钮只切换 UI，个性化底图需另行接入并真机验证。

Android 使用 AppCompat 深浅主题，并切换高德 `MAP_TYPE_NORMAL` / `MAP_TYPE_NIGHT`。

## 8. 部署地址与网络配置变化

后端早期在本机 `5173` 端口运行。小程序开发先后使用过：

- `http://127.0.0.1:5173`：微信开发者工具模拟器。
- 局域网 IP：真机与电脑同网调试；Windows 公用网络曾阻断访问，改为专用网络后恢复。
- `http://124.220.73.65:5174`：腾讯云公网 HTTP 地址。
- `https://pp.nuanzhualife.cn`：当前小程序生产 API 基址。

“启动 PC 端自动预览”能访问 HTTP IP，但手机二维码预览报 `request:fail url not in domain list`，原因是手机严格校验 HTTPS 和微信 `request` 合法域名。最终方向是域名 + HTTPS + 反向代理，Node 仍在内网监听 HTTP。

当前 `server.js` 默认端口是 `5174`；旧 README 和部分注释仍保留 `5173` 历史信息，本轮文档已以代码为准。

## 9. Android 客户端开发（2026-07）

项目新增 `WhereToPoop_apk/` 原生 Android 客户端，使用 Kotlin、Android ViewBinding、高德地图与定位 SDK、Retrofit 和统一后端。

当前 Android 已实现定位、城市选择、地点搜索、厕所查询、最近地铁站、深浅主题、后端步行路线和外部地图导航。Android 当前默认构建配置仍指向旧 HTTP IP，并允许明文流量；正式 HTTPS 切换状态无法确认。

## 10. 地铁状态颜色变化（2026-07 至 08）

早期规则是：有厕所绿色、没有厕所红色、不确定灰色。后来“不确定”统一改为橙色 `#F59E0B`，并同步到网页、小程序和 Android 的地图标记与列表状态点。

当前共享数据只有 `1` 和 `2`，尚无 `0` 记录。

## 11. 全球 POI 与按需地铁（2026-08）

项目在保留网页和 Android 国内链路的前提下，为微信小程序增加全球能力：

- 初版首次用 WGS84 和 Geoapify 识别国家，中国大陆再回到 GCJ-02；实测发现这会让国内启动受海外服务影响，随后改为 GCJ-02 候选范围内优先高德反查，只有海外才调用 Geoapify 并保持 WGS84。
- 六座重点城市加入硬边界文字搜索；当前位置和地图选点的海外 POI 查询不以六城为技术白名单。
- 海外厕所和地铁初版以 Overpass 为主、Geoapify 兜底；由于公共 Overpass 响应波动且串行超时造成数秒等待，2026-08-05 改为直接使用 Geoapify Places，默认 4 秒快速失败。
- 增加地图长按临时点和“选这里”，与文字地点统一为“先选定、再点击查厕所”。
- 厕所与地铁改为独立请求和 marker 图层，同一查询中心下互不清除。
- 取消小程序启动、定位和中心变化时的地铁预加载；地铁只由按钮查询 20 km 内最近 10 站。
- 国内地铁后端从逐城分页坐标索引改为一次中心周边查询，再匹配 `data/metro` 状态。

同时建立了后端供应商适配、坐标元数据和错误脱敏。随后针对中文等跨语言海外地点搜索接近 4 秒超时的问题，上游查询补充城市当地名称，文字搜索单独使用 6 秒超时，并增加 5 分钟进程内短缓存；第三方请求失败后的后端存活也纳入回归测试，相关自动化测试增至 17 个。六城后端链路已使用开发 Key 冒烟，微信真机长按、marker 和导航验收仍待完成。

2026-08-05 随后批准网页版全球支持方向。由于现有高德 JS Key 没有世界地图高级权限，决定国内网页继续使用高德/GCJ-02，海外网页使用 Leaflet 1.9.4、Geoapify Tiles 和 WGS84；国内保留网页内高德路线，海外使用外部导航。先建立 `docs/specs/web-global-support/` 和 ADR-0002，再进入代码阶段。

同日完成网页版实现：新增高德/Leaflet 地图适配层和查询中心纯逻辑，Leaflet 1.9.4 改为同源托管；浏览器定位按区域分流，城市切换不再建立查询中心，地点与地图选点采用两步流程。厕所和地铁改为独立图层，地铁只由按钮查询 20 km 最近 10 站；国内保留高德步行路线，海外以原始 WGS84 打开 Google Maps。后端 `/api/config` 增加独立浏览器瓦片字段，真实值只在被忽略的 `.env`。自动化增至 21 个测试，本地浏览器完成无锡和新加坡核心流程及 390/768/1440 布局回归；真实定位、移动端长按、外部导航弹窗和六城完整 UI 仍待发布前验证。

## 12. 当前有效

- 网页、小程序、Android 共用 `server.js` 和 `data/metro`。
- 小程序生产 API 基址为 `https://pp.nuanzhualife.cn`。
- 网页和 Android 保留内部步行路线；小程序使用 `wx.openLocation`。
- 地铁按 20 km 空间范围跨城市检索。
- 不确定地铁厕所状态为橙色。
- 小程序有分享和版本更新提示。
- 小程序支持海外 WGS84 厕所、地铁、六城地点搜索和地图长按选点。
- 地铁只按按钮加载最近 10 站；国内状态匹配来自 `data/metro`，海外统一未知。

## 13. 曾经实现但已移除

- 地铁 JSON 保存坐标。
- 用直线连接地铁站点。
- 后端逐站请求高德坐标。
- 小程序内部路线、路线按钮和路线结果页。
- 不确定状态使用灰色。
- 自制目的地导航页面方案。
- 小程序自动地铁预加载和后端活动链路中的逐城分页坐标索引。
