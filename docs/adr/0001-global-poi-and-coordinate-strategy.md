# ADR-0001：全球 POI 数据源与坐标策略

- 状态：Accepted
- 日期：2026-08-04
- 修订日期：2026-08-05（纳入实施前冲突确认）
- 决策范围：微信小程序全球厕所、地点搜索、地铁站与导航

## 1. 背景

拉了么现有微信小程序主要服务中国大陆：

- 腾讯原生地图作为底图；
- 高德服务提供国内厕所和地点数据；
- 国内地图坐标以 GCJ-02 为主；
- 用户当前位置是默认查询中心；
- 文字地点搜索可改变查询中心，当前采用“先选定，再点击查厕所”的两步流程；
- 半径变化立即查询厕所；
- 审查时的代码会在启动、重新定位、城市切换和地点选择时预加载地铁，专用按钮只展示已加载数据。

项目需要增加海外厕所和地铁站支持，首批重点验证新加坡、莫斯科、东京、伦敦、纽约和悉尼，同时技术能力不限制于这六座城市。

主要问题：

- 全球厕所和地铁数据源；
- 公共 API 成本与稳定性；
- 国内 GCJ-02 与海外 WGS84；
- 腾讯地图 marker 与 `wx.openLocation` 的坐标；
- 当前城市内地点搜索；
- 在不破坏国内业务的前提下增加地图选点。

## 2. 决策

### 2.1 客户端范围

本轮只实现微信小程序。网页版和 Android 后续单独决策。

### 2.2 底图

继续使用微信原生 `<map>` / 腾讯地图，不接入 Geoapify 地图瓦片。

### 2.3 数据源

中国大陆：

- 地点搜索、厕所继续使用现有高德链路；
- 地铁继续使用现有国内链路。

海外：

- 地点正向/逆向地理编码使用 Geoapify Geocoding；
- 厕所和地铁站主数据源使用公共 Overpass API；
- Overpass 失败后使用 Geoapify Places API 兜底；
- Overpass 公共接口不需要 API Key；
- Geoapify API Key 仅保存在后端。

### 2.4 坐标

- 中国大陆目的地：GCJ-02 用于腾讯地图展示和 `wx.openLocation`；
- 海外目的地：WGS84 用于腾讯海外地图展示和 `wx.openLocation`；
- 俄罗斯（包括莫斯科）属于海外 WGS84；
- 海外数据不得无条件转换为 GCJ-02；
- 每个地点对象必须显式记录坐标系。

### 2.5 查询中心

- 用户当前位置是默认查询中心；
- 国内现有文字地点搜索继续可改变查询中心；
- 新增地图长按选点作为第三种查询中心来源；
- 文字地点和地图选点只建立查询中心，不自动查询厕所或地铁；
- 切换城市时城市中心只作为地图视口中心，正式查询中心置空；
- 半径切换始终使用当前查询中心；
- 地铁专用按钮也使用当前查询中心。

### 2.6 业务触发

- 首次定位成功：自动查询厕所，不查地铁；
- 点击地点搜索结果：设置查询中心并清除旧结果，不自动查询厕所或地铁；
- 地图长按后点击“选这里”：设置查询中心并清除旧结果，不自动查询厕所或地铁；
- 点击“查厕所”：以当前查询中心和半径查询厕所，不查地铁；
- 切换半径：存在正式查询中心时立即查询厕所，不查地铁；
- 切换城市：只移动地图、清空查询中心和旧结果，不查厕所或地铁；
- 没有正式查询中心时，查询按钮和半径变化只提示先选择地点，不发请求；
- 地铁仅由专用按钮触发，以当前查询中心查询 20 km 内最近 10 个站点。

### 2.7 数量与降级

- Overpass 厕所结果按距离排序，最多展示最近 200 个；
- Geoapify 兜底最多展示最近 100 个，并提示结果可能不完整；
- 国内外地铁结果按距离排序，后端最多返回查询中心 20 km 内最近 10 个站点；
- 国内地铁改为按按钮执行周边查询，不再通过自动预加载触发冷启动多城市分页扫描；
- 第一版不做数据库、Redis或持久缓存；
- 必须实现请求去重、旧请求淘汰和快速失败兜底。

### 2.8 城市策略

六座城市是“重点验证城市”和快捷入口，不是 API 白名单。第一版不提供完整全球城市列表；其他海外城市可通过当前位置和地图选点使用。

### 2.9 结果与 marker 图层

- 厕所和地铁分别维护数据和 marker；
- 查询中心不变时，查询地铁保留厕所 marker，查询厕所保留地铁 marker；
- 查询结果面板可切换当前类型，但不得因此删除另一类型的数据；
- 文字地点、地图选点、重新定位或城市切换改变查询中心时，同时清除两类旧结果和 marker。

## 3. 决策理由

### 3.1 选择 Overpass 作为海外 POI 主接口

- 直接查询 OSM 原始标签；
- 一次可返回范围内多个厕所或地铁站；
- 不按返回每 20 个 POI 逐批消耗 Geoapify credits；
- 当前用户规模较小，适合以公共实例验证产品链路。

代价：公共实例没有商业 SLA，可能超时或限流，因此不能作为唯一无降级依赖。

### 3.2 选择 Geoapify 作为地理编码与兜底

- 提供全球正向和逆向地理编码；
- 支持城市范围过滤和位置偏向；
- Places API 可作为 Overpass 异常时的快速兜底；
- 与 OSM 数据体系兼容，规范化成本较低。

代价：需要 API Key，并消耗额度；因此 POI 兜底设置数量上限。

### 3.3 不更换腾讯底图

- 当前小程序已经使用腾讯原生地图；
- 更换底图会扩大开发与许可范围；
- 海外腾讯位置服务采用 WGS84；
- 当前目标是打通 POI 数据和交互，不是重构地图引擎。

### 3.4 不在第一版引入缓存

- 当前没有数据库或 Redis；
- 第一目标是验证六城数据、坐标和导航链路；
- 持久缓存会增加失效、部署和多实例一致性问题。

代价：公共 API 调用较多。第一版用请求去重、禁止拖动触发和地铁专用按钮控制负载；缓存进入下一阶段。

## 4. 被否决或暂缓的方案

### 4.1 Geoapify Places 作为唯一海外 POI 主接口

暂不采用。原因：在高密度区域返回大量结果时会增加 credits，且项目需要尽可能展示范围内厕所。

### 4.2 只使用公共 Overpass，不设兜底

不采用。原因：公共实例可能超时、429或临时不可用，用户寻找厕所时需要更稳定的降级。

### 4.3 使用公共 Nominatim 做地理编码

暂不采用。原因：公共服务有严格公平使用限制，会增加另一个公共基础依赖；Geoapify 已提供所需地理编码。

### 4.4 自建全球 Overpass / OSM 数据库

暂缓。当前用户规模不足以支撑部署和运维成本。

### 4.5 所有坐标统一转换成 GCJ-02

否决。海外腾讯服务、OSM、Geoapify及常见海外导航使用 WGS84，无条件转换会造成错误。

### 4.6 展示坐标使用 GCJ-02、导航另存 WGS84

海外不采用。腾讯海外地图展示和海外导航都使用 WGS84，因此当前无需维护两组不同数值；但代码仍应分离“取展示坐标”和“取导航坐标”的职责。

### 4.7 城市切换后自动查询

否决。用户切换城市后还需要选择具体地点；城市中心只用于地图定位。

### 4.8 厕所查询时自动加载地铁

否决。地铁只允许由专用按钮按需查询。审查时的代码预加载行为需要在实施中移除。

### 4.9 地点或地图选点后自动查询厕所

否决。文字地点和地图选点统一保留“先选定，再点击查厕所”的两步流程。首次定位成功和已有查询中心时切换半径是自动查询的两个明确例外。

## 5. 影响

### 正面影响

- 海外数据源与坐标规则清晰；
- 国内业务改动范围小；
- 支持全球当前定位和地图选点；
- 具备 Overpass 故障兜底；
- 地铁从自动预加载改为按需查询，降低不必要的高德配额消耗；
- 后续可增加缓存、更多城市和客户端。

### 负面影响

- 增加 Geoapify 外部依赖和 API Key 管理；
- 公共 Overpass 响应时间不可完全预测；
- OSM 地铁标签不统一，需要去重与兼容；
- 第一版无持久缓存，接口用量较高；
- 首次点击地铁按钮需要等待实时查询，不再依赖预加载结果；
- 海外腾讯底图的地铁线路显示质量不由拉了么控制。

## 6. 后续决策

后续单独评估：

- 厕所与地铁缓存；
- 第二个 Overpass 实例或商业 OSM 服务；
- 港澳台；
- 全球城市选择/搜索；
- 网页版和 Android；
- 地铁站厕所信息维护；
- OSM/Geoapify 署名 UI；
- 自有 POI 数据纠错与增量维护。

## 7. 实施约束

- 实施前必须完成现有代码对照；
- 发现冲突必须先向用户报告；
- C-01 至 C-04 已于 2026-08-05 完成确认，实施必须遵循本次修订后的触发与图层规则；
- ADR 不授权 Codex 擅自重构国内代码；
- 实际完成后由 Codex 同步现有架构、API、配置、测试和隐私文档。
